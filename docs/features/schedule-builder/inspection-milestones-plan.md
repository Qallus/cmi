## What already fits the engine

| Brandon's rule | The engine today |
|---|---|
| Every inspection is a milestone, duration 0, type Inspection | `kind: milestone`, `milestone_type: inspection` |
| Blue Stake, PT reports, surveys, certificates, outside approvals and utility releases are Internal | `milestone_type: internal` |
| Hold point: Finish→Start from the work before; the next work can't start until it passes | Finish-to-Start links with lag 0. The CPM forecast already moves everything behind a milestone when its date moves. |
| A failed inspection pushes everything behind it | Re-dating the milestone (the re-inspect date) re-forecasts every successor and critical path |
| Show on Master = milestones only | `master_display: milestone_only` |
| Phase IDs P00–P14 and step IDs as stable keys | New columns (Step 2); WBS can carry the phase ID |

## Build steps

### Step 1. The library in the database

- **Migration `inspection_library`:** one row per library milestone (e.g. `SCOT-M07`). The row holds:
  - jurisdiction, phase ID and phase, the reference doc's step ID, the Gantt name and the
    jurisdiction's own name
  - code and code basis, milestone type
  - the NEW / ADD / REN cells, kept as written ("Y", "If CMU", "—")
  - include-when, the predecessor and released hooks, hold point
  - request rule, ready-to-call checklist, repeats, show-on-master, notes, last verified date
- **`inspection_jurisdictions`:** one row per jurisdiction, holding:
  - scheduling method, portal URL, phone or text number
  - next-day cutoff (Tempe 24:00, Phoenix 21:00, Paradise Valley 15:00, Maricopa County 15:30;
    Mesa, Chandler, Cave Creek and Carefree to confirm)
  - inspection hours, notes
- **`inspection_task_hooks`:** hook text → template task title, from column D.
- **An import script** reads the R2 workbook, so a later revision from Brandon reloads the same way.

**Built (Nov 11, 2026), migration not yet applied:**
- `supabase/migrations/2026-11-11_inspection_milestones.sql`: the three tables, the job columns and the
  `inspection_milestones` flag (off).
- `2026-11-11_inspection_milestones_seed.sql`, generated by
  `node scripts/import-inspection-library.mjs <workbook> supabase/migrations/2026-11-11_inspection_milestones_seed.sql`.
  It holds 314 milestones (249 Inspection, 48 Internal, 17 Contract), 9 jurisdictions and 112 hooks,
  matching the workbook's Read Me counts.
- `lib/inspections/data.ts` reads it.

### Step 2. Job jurisdiction and scope

- Job Info gains three fields:
  - **Jurisdiction**, set by parcel, not mailing address (reference doc §13)
  - **Scope**: NEW, ADD or REN
  - **Conditions**: pool, CMU, gas, fire sprinklers, post-tension slab, right-of-way, site work,
    septic, hillside, stucco, basement
- Jurisdiction starts as a pick list. A Maricopa County parcel lookup could fill it in later.

**Built (Nov 11, 2026):**
- Job → Job Info → Job Details gets an **Inspections** section (flag on only). It has:
  - Jurisdiction, with a "Use … (from the city)" suggestion
  - that jurisdiction's request method and cutoff
  - Scope (NEW / ADD / REN)
  - Conditions in four groups
- `lib/inspections/conditions.ts` maps every "If …" scope cell in the library to a condition. A test
  checks all 314 rows. Seven phrases are left for the PM to confirm when loading: As needed,
  As required, Completion letter, If applicable, If listed on permit, If permit type and If required.
- Job saves clean the values server-side; unknown conditions are dropped.

### Step 3. Load inspections into a schedule

A new **Add inspections** action on a job's schedule:

- **Row picking:** filters the library by the job's jurisdiction and scope.
  - "Y" rows are included.
  - "If …" rows come from the job's Conditions. The PM confirms the list before anything is created.
- **Repeating rows** ask for a count: per grout lift, per pour, per ticket.
- **Each row becomes a milestone:**
  - zero duration; type Inspection or Internal, from the row
  - Show on Master = milestones only
  - step ID (`SCOT-M07`) and phase ID stored as keys
  - code, request rule and ready-to-call checklist on the item
- **Links:**
  - The milestone gets a Finish→Start link (lag 0) from the work task its predecessor hook maps to,
    and one to the task its released hook maps to.
  - A hook whose task isn't in this schedule goes on a short **"Unlinked inspections"** list for the
    PM, rather than being guessed.
- **Explicit chains:**
  - SCOT Final Site → Final building
  - MCO Final drainage → Building final, with at least one working day between
  - MCO Finished floor → Pre-slab (monolithic PT)
  - PV SWPPP → all other inspections
  - PV Roof nailing → dry-in
- **Template tasks:** the template's four inspection tasks are removed. Running it again on the same
  schedule skips rows already loaded (by step ID).

### Step 4. Inspection status and hold points

- **Status:** a new field on inspection milestones, using the values from Brandon's Read Me tab:
  Not Ready · Ready to Call · Requested · Scheduled · Passed · Partial · Failed / Correction ·
  Re-inspect Requested · N/A.
- **What each status does:**
  - **Passed** sets the actual finish, and the released task can start.
  - **Failed / Correction** asks for the re-inspection date and a note. The milestone moves to that
    date and the forecast pushes everything behind it.
  - **N/A** removes the milestone from the forecast but keeps it on record.
- **Hold point warning:** marking a released task started while its inspection isn't Passed shows a
  warning.
- **Request-by date:** each milestone shows when it must be requested, using the jurisdiction's cutoff.
  An example is "Request by Tue 9:00 PM (Phoenix IVR)". It appears in the three-week lookahead and on
  the Today page as "Call today for tomorrow's inspections".
- **Health tiles and reports:** "Waiting on Inspection" and the weekly update count these statuses.

### Step 5. The permit list wins

- On permit issue, the PM enters or pastes the permit's printed inspection list.
- **Reconcile screen:**
  - **Matched:** the library row takes the permit's name and code. This covers "Per permit" rows.
  - **Template-only:** marked N/A.
  - **Permit-only:** added as new milestones, with links chosen by the PM.
- **Verified date:** the job stores the date the list was verified against the permit.

## Decisions (Nov 11, 2026)

Brandon answered the first three open questions, and they are built:

- **Cutoffs are set in the dashboard.** They live in Settings → Scheduling → Inspections, along with how
  each jurisdiction takes requests, phone, portal, hours, notes and the last-verified date. Chandler,
  Cave Creek, Carefree and Mesa show "Cutoff to confirm" until someone enters them. Claude can edit
  them too, through `cmi_inspection_jurisdiction_save`.
- **Both PMs and Superintendents update inspection status.** The roles are controlled by Super Admins
  in the same card (`inspection_settings.status_editor_roles`; Super Admin and Admin always can).
  Step 4 checks this with `mayUpdateInspectionStatus`. Claude can read and change it through
  `cmi_inspection_settings` and `cmi_inspection_settings_update`.
- **Jurisdictions come from a list per job.** The list is edited in the dashboard: add, edit, or retire
  with `active`. Claude can change it, and can set a job's profile with `cmi_job_inspection_profile`.
- **Migration:** `2026-11-11_inspection_settings.sql`. Run it after the milestones migration and its
  seed.
